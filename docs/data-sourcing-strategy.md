## 1. 背景・目的

現状、`companies` / `salary_data_points` / `take_home_aggregates` は [scripts/seed.ts](../frontend/scripts/seed.ts) によるプレースホルダー企業（「サンプルテック株式会社」等）＋架空の年齢カーブ（`AGE_CURVE` の倍率）で構成されている。すべて `source = 'seed_estimate'`。

実企業名でサービスを成立させるには、信頼できる外部データソースへの移行が必要。本ドキュメントは SPEC.md §8 の未決事項「シードデータの具体的な出典・加工方法」に対する調査・提案であり、**実装の承認を得るための資料**。今回はデータ投入やスクレイピングの実行は行わない。

## 3. 推奨方針

### 3.1 基本方針：公的統計 × 有報のハイブリッド推定（スクレイピングは不採用）

- **④（口コミサイトのスクレイピング）は推奨しない。** 利用規約違反・著作権侵害のリスクが高く、「実質手取りの見える化」という信頼性訴求と矛盾する。提携可能な場合（データライセンス契約・API提供）のみ再検討。
- **⑤（出版物データ購入）はコスト対効果を見て中長期で検討**（初期スコープ外）。
- **短期の軸は ①賃金構造基本統計調査 ＋ ③EDINET有報** のハイブリッド。現行 seed.ts のロジック（`officialAvgSalaryYen × 年代別倍率 → calculateTakeHome`）は実は①③のハイブリッドと構造的に近いため、**倍率テーブル（`AGE_CURVE`）とベース年収の出典を実データに置き換えるだけで移行できる**。

### 3.2 具体的な置き換え方法

1. **ベース年収（`companies.officialAvgSalaryYen`）**: 上場企業は EDINET API から有報の「平均年間給与」を取得して置き換える（企業単位の確定値、`public_stat` 相当）。非上場企業は①②の業界×規模平均で代替（業界平均のため `seed_estimate` に近い扱いを継続）。
2. **年代別分解カーブ（`AGE_CURVE` の `multiplier`）**: 現在の手作業の推定値を、①賃金構造基本統計調査の「産業×企業規模×年齢階級」クロス表から算出した実際の比率に置き換える。
3. **職種別分解**: 現状 `position: '全職種'` のみ。①の「職種、年齢階級別所定内給与額等」表を使えば職種別も拡張可能だが、優先度は年代別分解の精度向上より低い。

これにより `salary_data_points.source` を `seed_estimate` → `public_stat` に正しく移行できる。**ただし、個々のレコードが「どの統計のどの年度の表に基づく推定か」をトレースできる必要がある**ため、§4 でスキーマ拡張を提案する。

## 4. スキーマへのマッピング・拡張提案

### 4.1 既存 `salaryDataSourceEnum` の使い方

現状の3値はそのまま使える：
- `seed_estimate`: 業界平均からの機械的な推定（非上場企業など、企業単位の実データがない場合）
- `public_stat`: 公的統計または有報等の公開情報に基づく値（①②③を使った場合はこれに変更）
- `user_submission`: 将来の `submissions` 承認分

### 4.2 追加で検討すべきフィールド（最小限の拡張）

現行スキーマには「どの統計を使ったか」のトレーサビリティがない。`source` の3値だけでは「賃金構造基本統計調査の令和7年調査」か「EDINETの2025年3月期有報」かを区別できず、更新時の差し替えやデータ鮮度表示（SPEC.md 機能③「サンプル数・データ更新日」）に支障が出る。そのため以下を提案：

```
salary_data_points に追加:
  source_detail   text null   -- 例: "賃金構造基本統計調査(令和7年) × EDINET 2025年3月期有報"
  source_year     int null    -- 調査年度・決算期年度
```

```
companies に追加:
  official_avg_salary_source_year int null  -- officialAvgSalaryYen がどの決算期の値か
  official_avg_salary_fetched_at  timestamptz null  -- EDINET取得日時
```

企業単位でなく業界単位の統計値（①②）を別テーブルとして持たせる案もある（`industry_wage_benchmarks(industry_id, employee_band, age_band, avg_annual_salary_yen, survey_year, source)`）。これにより「年代別分解カーブ」自体をバージョン管理でき、統計の年度更新時に過去データを壊さずに再計算できる。**推奨: この新テーブルを導入し、`take_home_aggregates` 生成ロジックが参照する「カーブ」をハードコードの `AGE_CURVE` 配列からDB駆動に変える。**

## 5. 継続更新の運用方式

| 方式 | 対象 | 頻度 | 自動化可否 |
|---|---|---|---|
| EDINET バッチ取得 | 上場企業の `officialAvgSalaryYen` | 四半期ごと（各社の決算発表タイミングはずれるため、書類一覧APIを定期ポーリングして差分更新） | 自動化容易（公式API、スクリプト化可能） |
| e-Stat バッチ取得 | 年代別分解カーブ（`industry_wage_benchmarks`） | 年1回（調査結果の公表タイミングに合わせる、例年末〜翌年） | 自動化容易（公式API） |
| 手動キュレーション | 非上場・統計がカバーしない企業の個別調整、異常値のレビュー | 都度 | 自動化不可（人間のレビューが必須。推定値である旨の免責表示とセットで運用） |
| `submissions` 承認フロー（将来） | ユーザー投稿 → モデレーション → `salary_data_points(source='user_submission')` へ反映 | 随時 | 半自動（投稿受付は自動、承認は人間） |

→ 結論：**年次バッチ（統計カーブ更新）＋ 四半期バッチ（EDINET差分更新）＋ 例外時の手動調整**という組み合わせが、公的統計の更新サイクルに最も合致し、運用負荷も小さい。

## 6. 法務・利用規約リスクまとめ

- **e-Stat / EDINET（①③）**: 政府提供の公式API・法定開示情報であり、商用利用・二次利用を前提とした設計（e-Stat API利用規約で商用利用可、クレジット表示が条件）。リスクは低いが、①APIを使ったアプリ公開時のクレジット表示の要否、③有報の記述部分（文章）を丸ごと転載しない（数値のみ加工して利用する）ことを徹底する。
- **人事院調査（②）**: 同様に公的統計だが、API提供がない表が多く、PDF解析のコストと将来の構造変化リスクがある。
- **口コミサイト（④）**: 利用規約でのスクレイピング禁止が一般的であり、著作権（投稿文章）・個人情報（投稿者属性）の両面でリスクが高い。**本提案では採用しない。**
- **出版物（⑤）**: 著作権保護あり。ライセンス購入なら合法だがコスト要検討。
- 全ソース共通で、SPEC.md §7 の「シードデータは推定値である」免責表示は継続必須。`public_stat` に移行しても「企業単位の実データではない年代分解」が含まれる限り、免責は外せない。

## 7. 段階的移行ステップ（提案）

1. **Step 0（現状）**: 全データ `seed_estimate`、架空企業名。
2. **Step 1**: スキーマ拡張（`source_detail`/`source_year` 等、§4）をマイグレーションとして追加。ロジック変更は行わない。
3. **Step 2**: EDINET APIクライアントを実装し、上場企業（まず少数の実在企業でパイロット）の有報から平均年間給与を取得 → `companies` を実データに更新。`officialAvgSalaryYen` の出典が変わるのみで、`salary_data_points` の生成ロジック（年代カーブ適用）は現状維持。
4. **Step 3**: e-Stat APIから賃金構造基本統計調査の産業×企業規模×年齢階級表を取得し、`industry_wage_benchmarks` を構築。`AGE_CURVE` のハードコードをこのテーブル参照に置き換え、`salary_data_points.source` を `public_stat` に変更。
5. **Step 4**: 四半期/年次バッチ化（スクリプトの定期実行、運用ドキュメント整備）とデータ鮮度のUI表示。
6. **Step 5（将来フェーズ）**: `submissions` の投稿フォーム実装・モデレーション運用。

各ステップは独立して価値があり、Step 1-2 だけでも「実在する上場企業の公式年収」という信頼性の高い訴求に進化できる。Step 3 以降で年代別分解の精度が統計的根拠を持つようになる。
